# CLI reference

`clawstrum help` prints the same list in short form. Every command works on the state directory `CLAWSTRUM_HOME` (default `~/.clawstrum`). The command dispatch is in [src/cli-main.ts](../src/cli-main.ts) and [src/workflow-cli.ts](../src/workflow-cli.ts); see [operations](operations.md) for how the pieces fit together in a running installation.

| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `clawstrum backup DIRECTORY`                                                | Snapshot the state directory and database. The daemon must be stopped                          |
| `clawstrum backup live DIRECTORY [--keep-last N --keep-days N]`             | Snapshot the database while the daemon runs. Needs Node 22.16 or newer                         |

| `clawstrum restart status` / `restart cancel`                               | Show or cancel a pending restart                                                               |
| `clawstrum apply [--no-test]`                                               | In a source checkout: type-check, build and test, then request a restart on the new build      |
| `clawstrum rollback`                                                        | Restore the build from before the last `apply` and restart                                     |
| `clawstrum gc --before DATE [--apply]`                                      | List transfer files older than DATE; `--apply` removes them. Run it offline                    |

| `clawstrum mcp`                                                             | Internal: the agent's tool server, started by the daemon for each run                          |

Commands that inspect or queue work open the database even while the daemon runs. Queued controls take effect at the daemon's next tick, whether or not the provider is responding.

## Startup and shutdown

`clawstrum start` reads the bot token from the variable named in `discord.tokenEnv`, takes the daemon lock, connects to Discord, registers the `/clawstrum` command, reads messages missed while it was down, and recovers interrupted work. It then logs a `ready` line with the agent name, version and process ID, and runs its loop every 500 ms.

Only one daemon can run per state directory. The lock is an exclusive SQLite transaction on `daemon-lock.db`, which the operating system releases when the process dies. `daemon.lock` beside it records the process ID, host and start time for diagnosis. This lock is local: several hosts sharing one state directory are not supported, and the database belongs on local storage.

On SIGINT or SIGTERM the daemon stops its loop, aborts and waits for active work, disconnects from Discord, releases the lock and closes the database. The unit from `clawstrum service` uses absolute paths, `Restart=on-failure`, `RestartSec=5`, `StartLimitIntervalSec=0`, `KillMode=control-group` and `TimeoutStopSec=30`. It adds no filesystem sandbox. Only a systemd unit is generated; on macOS, use your own service manager or keep `clawstrum start` running in a terminal.

## Diagnostics and export

`clawstrum doctor` checks the database's integrity, the bot token, provider runtime versions and local sign-ins, and the daemon: its heartbeat, overdue or failed schedules, stalled queued work, stale running turns, failed deliveries, and file permissions on `.env` and the configuration. Input waiting behind an active turn does not count as stalled. A failed delivery stays reported until it is retried. A fresh installation that has never run is not reported as a dead daemon. Version probes time out after ten seconds and sign-in probes after 20 seconds. `doctor` prints no credentials and sends no model or Discord request.

`clawstrum smoke` is the model test. It makes a temporary workspace, asks the provider for a fixed answer with no tools, gives up after two minutes, and removes the workspace.

The database records the agent's output, tool activity, usage, handoffs, interruptions, delivery results and engine errors. The console log is JSON. There is no metrics server. Usage reports state which counters are missing; they are not a meter of subscription quota. See [research continuity](research-continuity.md).

`clawstrum export` writes the conversation's metadata, inputs, events, outgoing messages, runs, tasks and task runs. It does not include workspace files, provider transcripts or credentials, but tool output and errors can contain private details. The file is written with private permissions.

## Backup and upgrade

`clawstrum backup DIRECTORY` takes the daemon lock, refuses if the daemon runs or the destination exists, copies the state directory, makes a consistent database snapshot with `VACUUM INTO`, and renames the finished directory into place. Stop the service first. Account homes and workspaces outside the state directory, and symlink targets, need their own backups. Restore to the same absolute path, or update the stored paths yourself. `clawstrum gc --before DATE --apply` removes old transfer files offline and keeps files that pending or failed inputs and deliveries still need; database history is kept.

A new version migrates the database schema in a transaction when it first opens it; a failed migration rolls back, and a database from a newer version is refused. Some upgrades also need `clawstrum memory migrate --apply` before the first start; see [memory lifecycle](memory-lifecycle.md#existing-installations). To upgrade, back up offline, install the new package and restart under the supervisor; then check the running version. To roll back after a schema change, restore the complete backup together with the matching build. Do not run an older build against a migrated database. Clawstrum has no automatic updater.
