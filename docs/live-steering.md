# Live user steering

When a user sends more text while Claude or Codex is working, Clawstrum can forward it into the existing provider conversation. The worker and native session stay alive. The provider runtime decides when it processes that input; this does not interrupt an already running shell command or guarantee an immediate change in the model's behavior.

Claude uses the SDK's [streaming input interface](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode). Codex uses the bundled runtime's [App Server interface](https://learn.chatgpt.com/docs/app-server). Steering is enabled automatically for eligible Claude and Codex lead runs, including scheduled and recovery turns, with the existing Discord authorization and full host access settings. No additional credentials, configuration, tools or database migration are needed.

## Admission and ordering

`Engine.tick()` considers steering even when all conversation slots are occupied. The existing debounce and typing deadlines apply. A run must have reported readiness, have an open injector, and have no cancellation, shutdown or provider-process completion recorded. A delivered `final=true` answer does not close live intake: Claude or Codex may continue tool work or background work afterward. New questions can enter that same stream without waiting for a native result or interrupting tools. The provider chooses when to consume them.

This prevents a specific failure: the agent answers a side question with `final=true`, continues a long experiment, and the user's subsequent progress question waits indefinitely even while experiment updates keep arriving. Answer delivery, provider execution and user-input admission are separate states. The final flag controls duplicate answers and reply scopes, not whether a later question can reach the agent.

Only newly queued user text is eligible. Scheduled and recovery lead runs also accept arriving user text; an internal task must not hold the conversation’s user queue until the whole task finishes. Accepted input changes the run from task-only to interactive. Explicit scheduled execution budgets remain in force for the already-started invocation. If that cap is reached, unanswered accepted user input returns to the normal interactive queue while the scheduled task retains its budget failure. Research subagents instead accept explicit lead corrections through `research_steer`, with their own durable queue and acknowledgment states; see [subagent steering](research-continuity.md#steering-and-continuing-subagents). Within the user queue, an older delayed retry, an existing logical retry batch, or any attachment stops admission; later text cannot jump that barrier. Attachments retain the normal download pipeline.

Each injection includes at most 20 complete JSON records containing message ID, role, author, local send time (`at`, in `runtime.timezone`) and text. The complete payload must fit `runtime.promptChars`. An oversized first record remains queued for ordinary context construction. Message content is not truncated and then acknowledged as if the full text was supplied. Only one IPC acknowledgment can be outstanding per conversation.

The injected text identifies new user input but adds no acknowledgment or writing-style rule. Those preferences come from the current AGENTS.md instruction sections, including live edits. The default shared policy asks for one specific acknowledgment and a coherent answer for related pending messages, treating corrections as part of the ongoing request. It does not require one answer per Discord message. Editing or removing that policy affects follow-up messages as well as fresh turns. Existing installations retain their own AGENTS.md; update any older “one question, one answer” policy if it unintentionally separates related questions.

## Transport and persistence

1. The engine records pending IDs in memory and sends their text through the supervisor's `inject` IPC message. The durable input remains `queued` at this point.
2. The worker advertises `injector_ready` only after its provider installs the injector. Claude passes input to `TurnStream`; Codex sends `turn/steer` with the current thread and expected turn IDs. An `injected` event reports acceptance: into Claude's stream, or by a matching Codex RPC response. A worker with no injector rejects input. Direct and supervised providers share the same acknowledgment behavior.
3. A positive acknowledgment can claim only pending IDs from this session that still represent new queued user input. One transaction moves them to `running`, attaches the existing logical batch, updates `runs.message_ids`, and writes `steered` events. Only after commit does the engine update the in-memory message list and native usage estimates.
4. Finish, transient retry, quota/account handoff and restart recovery use the extended batch. Handoff context includes acknowledged steering. Messages without a positive acknowledgment retain their normal follow-up path. On positive acknowledgment, the same transaction checks the final flag and reopens the answer if necessary, including when the earlier final raced the acknowledgment. That race cannot discard accepted input or disable later steering. Rejected input does not reopen the previous answer.

A send failure or rejection disables that attempt's injector. A missing acknowledgment prevents further injection during that attempt, so the daemon does not repeatedly send an uncertain batch. The existing worker lifecycle and timeout settings still apply; once it ends, unacknowledged input remains available for a normal run. Worker IPC has no separate acknowledgment timeout; Codex RPC requests have a 30-second response deadline. A late or missing response never causes blind resubmission within the active run.

## Requests after a final answer

When new text is accepted after a final answer, one transaction marks already-answered inputs done, preserves earlier accepted inputs whose provider intake has not started, clears the current final flag and advances a durable reply scope in schema-3 metadata. The existing MCP process reads that scope on each message/file/schedule operation; automatic results use it too. Old output cannot satisfy or deduplicate the new answer, even when its text is identical. Retries and restart recovery keep the scope and do not replay the previously answered inputs. A rejected injection changes none of this state. Background work is not terminated to make room for the request.

There is another ordering: Claude can accept follow-up input before an earlier question's final reply, then start processing that follow-up later in the same live stream. Clawstrum records `input_started` at the lead's `UserPromptSubmit` hook, matching a complete submitted prompt or its exact newline-joined batch back to accepted Discord IDs. Matching fragments or IDs found inside prose is not sufficient. The pinned CLI's first lead stream/assistant frame also supplies consumed prompt UUIDs as a fallback; duplicate stamps and subagent events cannot reopen a reply. Both paths are needed: messages folded into an already-running typed turn fire the prompt hook without receiving new UUID-stamped reply frames.

If the final flag still belongs to the earlier answer, intake reopens the reply scope and preserves all not-yet-started input. Newly queued related questions can enter ongoing work regardless of the final flag. Producers providing neither a matching prompt hook nor consumption stamps cannot prove when input started, but this does not block further transport admission. Stream deltas are not copied to portable history; complete messages retain the existing history path.

Transport acceptance (`steered`), provider consumption (`input_started`) and completion are distinct. This matters when investigating apparent one-at-a-time replies: messages may be batched together but reach the provider after an older answer has already been sent. Neither admission nor consumption proves that the model addressed every question. Already-sent Discord messages cannot be retroactively combined.

Input admission is durable and attempts a small Discord reaction, but emits no automatic queue message. Both providers are instructed to send a short, task-specific, non-final acknowledgment in the conversation before investigative work, including on live steering. The acknowledgment names the intended next action in the model's own words rather than repeating a generic receipt; the same instruction applies with custom identity files. It is generated within the normal agent turn, not a separate acknowledgment model call. Useful waiting/retry notices still use real message threads; see [notice routing and fallbacks](setup.md#discord).

## Claude stream lifecycle

`src/turn-stream.ts` yields the initial prompt and subsequent injected batches as SDK user messages with unique UUIDs. It tracks outstanding delivered inputs, buffered inputs and observed background tasks. Claude can combine several sends into one turn, so results acknowledge the specific `user_message_uuids` (or single `user_message_uuid`) they completed. A duplicate or unrelated acknowledgement cannot consume a newer send. Older producers without these fields retain conservative one-at-a-time completion tracking. Normal closure requires a result, no outstanding or buffered input, no held background tasks, and no active turn started by the CLI itself. After observed background work settles, `runtime.inputReleaseGraceMs` (default 10,000 ms, configurable from 0 to 60,000) keeps stdin open for delayed task-notification turns. A notification turn or new user input cancels the pending close; its completion starts a new grace period. Ordinary turns without observed background work close immediately. This prevents closing the SDK control channel while notification tools still need hook responses; it does not delay already-sent Discord replies.

Research background-task holding uses the same implementation through `BackgroundInput`, avoiding two separate task-notification state machines. Abort closes the iterator immediately, releases a waiting reader and prevents buffered input from being yielded. Provider cleanup also closes it. EOF while accepted steering is still unfinished raises a transient failure instead of returning the first answer as completion of the entire batch. The last nonempty successful result remains the automatic reply, as with the existing background-task behavior.

On resume, Claude can first emit an uncorrelated result with zero model turns for a previous background task. That notification does not complete the newly submitted prompt or close its input stream. Explicitly acknowledged zero-turn commands still complete normally. Native compaction status messages count as provider activity, so a progressing compaction is not mistaken for silence; the ordinary silence timeout still applies when those updates stop.

## Codex transport and lifecycle

`ProviderRequest.liveInput` selects `src/codex-app-server.ts` for all Codex lead turns and research subagents. Requests with `contextRefresh`, including scheduled lead jobs, also use App Server for instruction updates. Ordinary SDK smoke calls retain `@openai/codex-sdk` execution. The TypeScript SDK pinned at 0.154.0 does not expose steering. The adapter launches that SDK's bundled Codex runtime over local stdio; it adds no Python dependency, public listener or API-key authentication. Explicit executable overrides must support the corresponding App Server protocol.

The connection initializes, starts or resumes a thread with the account's workspace, model, Clawstrum instructions and MCP server, then starts one turn. Authentication remains forced to ChatGPT, the selected `CODEX_HOME` is preserved, and sandbox/approval settings remain full access/never. An unexpected execution or filesystem approval receives the already-authorized acceptance; unsupported interactive questions return an explicit protocol error instead of fabricating a user answer.

Input is acknowledged only when `turn/steer` returns the expected active turn ID. A wrong-turn response, rejection or disconnect leaves it queued. If `turn/completed` precedes a pending steering response, the adapter settles those responses before returning the final result. This lets the engine persist accepted IDs before completing the batch. It never starts a second model turn to imitate steering.

Thread and turn IDs filter events. Completed assistant items supply the final reply; tool events, sampled text deltas, token usage and reported quota windows feed existing diagnostics/account routing. Text deltas are sampled at most once per second to avoid a database write per token; completed messages retain full text. Structured quota, authentication, context and transport errors use the existing handoff/retry paths. A missing saved rollout requests a fresh portable session. Reasoning text is not copied into normalized history.

Abort cancels outstanding requests, gives `turn/interrupt` up to one second to acknowledge, then closes the child with bounded TERM/KILL cleanup. The enclosing worker supervisor still owns process-group cleanup. Both backends share the existing total run deadline.

## Delivery limits

An acknowledgment means the provider transport accepted the input; it is not evidence that the model understood or acted on it. Claude closure uses input IDs acknowledged by the pinned runtime; Codex uses its guarded turn acknowledgment and completion events. A process or host failure between provider acceptance and SQLite acknowledgment can cause replay. External tool side effects are not exactly once. Existing explicit `send_message(final=true)` semantics still mean the agent asserts that the batch is answered.

Text steering shares the current conversation. Corrections before a final answer keep the existing deadline. A new request accepted after a final answer receives a fresh absolute deadline, while preserving the live provider and its background tasks. Attachment injection is not implemented here. An intake reaction does not promise immediate model attention. The task-specific acknowledgment arrives only when the model starts processing the request.

## Verification

The steering tests cover stream closure and abort, background holds, surplus background results, premature EOF, positive/rejected/missing acknowledgments, session and pending-ID validation, duplicate acknowledgments, ordering barriers, bounded batches, typing/debounce, full concurrency, final-reply races, cancellation, crash recovery and quota handoff in both provider directions.

Compiled Claude and Codex regressions also accept follow-ups after a delivered final while the provider turn remains active, including a Claude tool with no native result yet. Shared engine tests cover batching those follow-ups, a final racing acceptance, continued admission after that race, and recovery of previously accepted inputs whose consumption has not started.

The completion regressions include coalesced sends, duplicate and unrelated result IDs, buffered input, and background holds. The CLI can return fewer results than prompts submitted, with one result acknowledging several combined prompts, so counting one completion per submitted message can leave an answered turn open until its silence timeout.

Additional consumption regressions cover stale final flags, exact prompt matching, coalesced intake, duplicate hook/frame notifications, retained unfinished input and restart recovery. The compiled-worker fixture exercises both prompt-hook callbacks and reply-frame stamps through the installed SDK. A subscription-backed active-turn probe injected two follow-ups during a six-second Bash command: Claude folded both into the same result, using prompt hooks without new stamped reply frames. The provider probe verifies one intake event per follow-up and an answer containing all three requested markers.

A contract test uses the compiled engine/supervisor/worker, the installed Claude SDK and a real local JSONL subprocess. It verifies that both inputs reach the same subprocess, the second input joins the original durable run, and the final result reaches the outbox. These tests require no live account or Discord interaction. Real-model responsiveness and live Discord acceptance of this new feature have not been established by these local tests.

`test/codex-steering.test.ts` adds protocol subprocess coverage for accepted, rejected, mismatched and late acknowledgments, transport loss, malformed frames, cancellation during startup and active work, native resume, quota/auth classification and full-access approvals. Compiled-worker tests verify durable outcomes on success, rejection and disconnect. A separate no-model test launches the actual bundled Codex App Server, initializes a temporary empty profile, creates an ephemeral thread and verifies that steering without an active turn is rejected. No subscription credentials are used in those tests.

The responsiveness regressions also exercise post-final steering through the compiled supervisor, worker and installed Claude SDK with a controlled subprocess, reply-scope persistence, repeated answer text, rejection and restart behavior. `test/permission-gate.test.ts` exercises full-access headless approvals and cancellation through the installed SDK control protocol. These tests establish transport/state behavior, not a guarantee that every model follows the acknowledgment instruction.

If a human message remains queued behind a quiet, ready provider for two minutes with no foreground tool running, Clawstrum saves diagnostics and hands the queued work to a new turn on the same native session. This also covers stale background-task counts after an injector becomes unavailable. A queued task wake is handed off under the same conditions when the provider has already returned its result, so a watch expiry cannot wait behind an abandoned background command. The default `runtime.queuedInputTimeoutMs=120000` is independent of the absolute turn timeout; zero disables recovery. Completed requests are retained as done and unfinished requests remain queued. Provider cancellation can stop its native local child processes; it does not cancel independent remote jobs or Clawstrum research subagents. See [performance diagnostics](performance.md#queue-recovery-and-maintenance-pacing).
