# Computational research in Clawstrum

The research profile gives both Claude and Codex open-access paper retrieval, registry-backed citation records, structured research notes, bounded subagents, Slurm preflight, and durable job watches. Claude additionally receives SDK hooks and background-task lifetime handling. The profile, core consolidation and Slurm helpers are enabled by default, with full host access and advisory validation. Explicit `false` settings disable individual features; `research.enabled=false` disables research tools; core history/compaction/consolidation are independent. Set `research.validation` to `strict` explicitly for targeted denials, or `off` to disable checks.

## Configure and use

On an initialized installation:

```sh
clawstrum research enable --email you@example.org
# Re-enable Slurm if it was explicitly disabled:
clawstrum research enable --slurm
clawstrum doctor
```

Restart the daemon to load the configuration. Install Poppler’s `pdftotext` if you want PDF extraction, or set `research.pdftotext` to its executable path. HTML/XML fallbacks work without Poppler. Slurm commands must be available to the daemon; their paths are configurable. No cluster, account, partition, GPU model, scratch path, or personal contact is built in. These dependencies are optional for the core harness.

In Discord, ask the agent to use the research tools: “Find the full paper, check the DOI and authors, record the experimental method, run a small preflight, then watch the job and report its result.” The agent still decides how to conduct the research. An available subscription profile runs model work; deterministic retrieval and polling do not make model API calls.

The CLI exposes the same operations for inspection and automation:

```sh
clawstrum status
clawstrum research paper SESSION --input paper.json
clawstrum research cluster SESSION --input job.json
clawstrum research status SESSION --input status.json
```

`paper.json` can contain `{"id":"arXiv:2401.12345v2"}`; replace the example with the intended paper. `status.json` can contain `{"collection":"jobs"}`. Obtain `SESSION` from `clawstrum status`. CLI subagent/job creation uses the supplied `key` across that conversation’s CLI calls; use a new key for intentionally new work. MCP keys are scoped to a logical parent input, so retries and account changes reuse a request’s key.

## Literature search

`research_search` finds papers for one question. It runs OpenAlex keyword search (one call per `kw`), OpenAlex semantic search (`q` and each `para`, once unfiltered and once for the last two years, one request per second) and an arXiv search over the first three `kw` for the last 18 months. When the year-filtered semantic call fails, as it does with a 504 on about a third of queries, a keyword search with the same filter stands in without a warning. Missing abstracts are filled from Crossref. `seeds` (DOI, arXiv ID or OpenAlex W-ID) are always candidates and are expanded in the first hop; `exclude` (IDs or exact titles) never become candidates or seeds. `from`/`to` bound the publication year.

Every candidate is graded by Jev through the decisions client: the probability that the paper directly addresses the question for this researcher, with `ctx` (three or four lines on the project and why you are searching) passed as project context. Ranking quality drops without it. Calls run in parallel up to `decisions.maxConcurrent` (at most 24), with a 20 s limit and three attempts per paper. If the client reports Jev disabled, no key, a rejected key or an exhausted daily budget, the run is ranked by bm25 from the start. If Jev fails mid-run (the first 12 calls all fail, 8 papers in a row, or more than 25 % of 20 or more), the whole run is re-ranked by bm25. bm25 is word overlap with the question, context and keywords, fused with search rank. Scores from the two graders are never mixed. The result names the grader, and `fallback` gives the reason whenever it is not Jev.

Expansion adds the references, 25 most-cited and 25 newest citers of the best-graded papers (P ≥ 0.5, at most five per hop, plus every seed in hop 1). A second hop runs only if the first put at least two new papers into the top `k`. bm25 runs one hop from its top three. A run is bounded to 240 s and to $0.10 of OpenAlex spend, read from the response cost headers.

The full result, every candidate with score, grader, abstract and where it came from, is written to `research/searches/` under the Clawstrum home. The tool returns the grader, fallback reason, warnings, counts, cost, seconds, the artifact path and the top `k` rows (rank, score, title, year, first author, DOI/arXiv/OpenAlex ID). The OpenAlex key is read from the environment variable named by `research.openalexKeyEnv` (default `OPENALEX_API_KEY`); without it the run warns and calls OpenAlex unauthenticated. `research.email` is sent as `mailto` to OpenAlex and Crossref when set. Keys never appear in results, warnings, errors or the artifact.

## Paper retrieval and citation evidence

`literature.ts` resolves arXiv through PDF, arXiv HTML and ar5iv, retaining the requested version in the identifier and URL. DOI retrieval collects PMC full text, optional Springer OA JATS, eLife reviewed preprints, Unpaywall locations ordered with repositories before publishers, and finally a DOI landing-page PDF link. A PMC identifier comes from Europe PMC search or the NCBI ID converter. Returned identifiers must match the request. Europe PMC's `fullTextXML` route is offered for its open-access subset; NCBI `efetch` is attempted for any resolved PMCID because some author-manuscript deposits marked `isOpenAccess=N` are readable. Archive availability still determines whether extraction succeeds. Both PMC routes inspect front matter to distinguish an `acceptedVersion` from the published version, and reject contradictory DOI metadata when present. Structured records require a complete body element; front matter alone is not full text. DSpace download links get an alternate content endpoint. A given URL can supply a PDF or a landing page with a PDF link.

PMIDs and PMCIDs (bare or as PubMed/PMC URLs) go straight to the PMC routes. bioRxiv and medRxiv DOIs (`10.1101`, `10.64898`) use the preprint servers' details API for the latest version's PDF, because the publisher host throttles automated clients. OSF preprints are read through the OSF API. An OpenReview ID or URL looks for the same paper by exact title on arXiv, then Crossref, before the OpenReview PDF. A ResearchGate URL, which refuses automated clients, is resolved by the title in its slug to an arXiv ID or DOI; the title match is strict, so a near miss returns nothing rather than another paper. Plain titles are not accepted as input.

When every free location has failed and the environment variable named by `research.openalexKeyEnv` holds a key, the stored copy at OpenAlex (GROBID XML, then PDF) is tried. OpenAlex charges these downloads against the key's daily budget, so the rung is skipped while the remaining budget, read from the response headers, is below `research.openalexReserveUsd`. The key is sent only as a request header and never appears in attempts, manifests or errors.

eLife's [reviewed-preprint endpoint](https://github.com/elifesciences/api-raml/blob/master/src/api.raml) returns its latest version. The adapter verifies the returned article ID and numeric version. A versioned DOI such as `10.7554/eLife.110287.1` is refused on this route if the API returns another version; it is never silently replaced by that newer text. An unversioned identifier can use the returned version, recorded as `reviewedPreprint-vN`. The API's `indexContent` field is for search indexing, so nonempty text alone is insufficient: recognizable article-body section headings and the character minimum are required. This is a conservative completeness heuristic and may reject unusual documents. The source JSON is retained, including assessment text when supplied. This route does not provide arbitrary historical versions.

Requests have time and byte bounds. PDFs require a PDF signature and successful host extraction; known challenge pages, HTML substituted for a PDF, landing pages and short extraction stubs are rejected. Poppler's default mode attempts reading order for `textPath`. A separate `-layout` copy, when extraction succeeds, is returned as `layoutTextPath` for inspecting tables; it can interleave columns and should not supply prose quotations. Check quotations, equations and tables against the source document: neither extraction mode guarantees faithful reconstruction. Failure of optional layout extraction preserves usable prose, while cancellation still aborts the request.

The manifest records source, version, extraction versions and hashes. Older PDF caches made using layout as the default are refetched. Older PMC/eLife caches that predate structured-body/version checks are also refetched. A changed or missing optional layout file is omitted from a cache hit rather than presented as verified table text. The default minimum is 1,000 extracted characters. If every route fails, the result is `no-fulltext` with reasons. Cache hits verify the prose hash and preserve retrieval provenance; caches do not otherwise expire automatically. Use `refresh=true` for a changed source, especially with unversioned identifiers. Scanned documents may need a separate OCR workflow.

Unpaywall requires the configured contact email. Crossref requests add `mailto` when available. Springer is skipped unless the environment variable named by `research.springerKeyEnv` is present. It is an optional literature-service key, not a model billing credential. URL credentials/contact parameters are redacted in returned provenance URLs; transport failures do not echo secret request URLs. No shadow-library route is included. See the official [Unpaywall API](https://unpaywall.org/api/v2), [Crossref access documentation](https://www.crossref.org/documentation/retrieve-metadata/rest-api/access-and-authentication/), [Europe PMC service](https://europepmc.org/RestfulWebService), [NCBI ID converter](https://pmc.ncbi.nlm.nih.gov/tools/id-converter-api/), and [Springer API description](https://support.springernature.com/en/support/solutions/articles/6000195668-springerlink-api-details).

Citation verification checks the returned DOI, or available arXiv canonical identifier, and requires a title and authors before inserting a SQLite record. It stores retrieval time, response hash, source path, authors, title, year, venue and Crossref correction links when supplied. DOI resolution tries Crossref, then DataCite only after a Crossref 404. Throttling, cancellation and invalid metadata do not trigger this fallback. DataCite evidence retains organizational/personal creators, publisher/container and version relationships; those relationships are not findings of a correction or retraction. A metadata check compares normalized titles and author names and tolerates a one-year publication/preprint difference. Quote checks match normalized text in the explicitly supplied file. They do not establish that this file belongs to that identifier, validate scientific assertions, interpret a correction notice, or make the editable ledger tamper-proof.

### Scan a report or reply

Use `research_citation` with `{"action":"scan","path":"report.md"}` or `{"action":"scan","text":"..."}`. Paths resolve against the conversation workspace; files/text are limited to 2,000,000 bytes. This action uses saved registry records without a network or model call. Resolve missing identifiers with `action=verify`, then rescan.

The scanner checks recognized local author–year pairs and plain BibTeX author/title/year fields, retaining repeated identifiers, DOI parentheses, SICI-style suffixes and requested arXiv versions. Bare modern arXiv identifiers are also recognized. Feedback includes the record’s actual metadata and line number. It reports ambiguous associations and leaves unrecognized syntax unverified; `ok` means no detected discrepancy. It excludes fenced examples and automatically scans only `.md`, `.markdown`, `.tex`, `.bib` and `.rst` attachments/writes. PDF attachments are not parsed by this delivery check. Claude Edit previews catch changes beside unchanged identifiers, excluding findings already present before the edit. See [the parser boundaries](hooks-and-gates.md#citation-implementation) before interpreting a clean scan as coverage of a whole manuscript.

## Computational jobs

A submission input looks like this:

```json
{
  "action": "submit",
  "key": "pilot-seed-42",
  "batch": {
    "script": "/project/experiment/run.sh",
    "cwd": "/project/experiment",
    "inputs": ["data/input.npy"],
    "resources": {
      "time": "00:10:00",
      "mem": "2G",
      "cpusPerTask": 1,
      "output": "logs/%j.out"
    }
  }
}
```

Use `action=preflight` with the same `batch` to inspect first. Resources also accept `partition`, `account`, `nodes`, `gres`, `array`, `error`, `constraint`, and `qos`. Other Slurm directives can live in the batch script. `cwd` defaults to the conversation workspace. Declared inputs resolve against it; the script path resolves against the workspace. The helper records a copy of the batch script, not a snapshot of the project, environment, datasets or binaries. Record those revisions and seeds with `research_note`.

Preflight checks script readability/shebang, declared input readability, working directory and free bytes; queries `sinfo`, `sshare` and the caller’s `squeue`; and invokes `sbatch --test-only`. Site-information failures are warnings. It also reads the script body for three mistakes the scheduler accepts and the job then fails on: a `#SBATCH` directive placed after the first command, where Slurm stops parsing and silently drops it; `conda activate` without a sourced shell hook, which exits non-zero under the non-interactive shell a batch job gets; and an interpreter invoked from `PATH` rather than by absolute path, which resolves to whatever the compute node’s environment happens to hold. The first two are errors and the third is a warning, because `PATH` interpreters are site-dependent and legitimate on many clusters. Invalid scripts/inputs or failed scheduler validation stop this helper’s submission. There is no human approval dialog. According to the [Slurm sbatch manual](https://slurm.schedmd.com/sbatch.html), test-only validates the script/scheduling request without submitting a job; it is not a simulation or correctness test of the program.

Submission passes arguments directly to an executable, with an explicit working directory, captured script and `--comment=clawstrum:<record-id>`. Before calling `sbatch --parsable`, SQLite records `submitting`. A recognized acknowledgement records the scheduler job ID/cluster and starts a watch. A timeout, unrecognized reply, or daemon restart during submission changes the record to `unknown`. Repeating the same key returns that state and never automatically resubmits. A changed script or payload with the same key is rejected.

For an unknown submission, inspect scheduler records for its Clawstrum comment. Once the actual job is identified, call:

```json
{ "action": "adopt", "id": "CLAWSTRUM_RECORD_ID", "jobId": "123456", "cluster": "OPTIONAL_CLUSTER" }
```

Remove `cluster` when unnecessary. Adoption is an explicit assertion by the caller that reconciliation has identified the right job. It is not an automatic search or proof of identity. Existing external jobs can be registered with `{"action":"watch","jobId":"123456"}`.

Watches survive daemon restarts. The default poll interval is five minutes, with 288 checks (about one day when uninterrupted). There is no model call for each poll. The monitor combines queue state with accounting state and exit codes, preserves step-level `MaxRSS`, and distinguishes missing accounting from completion. Observations add explicit OOM, timeout, preemption, node-failure, cancellation and other failure classifications with evidence and suggested checks; generic failures and exit 137 do not prove OOM. No automatic resubmission is introduced. For submitted arrays with a recognized index expression, all expected indices must be represented before completion is reported. The index parser supports lists/ranges/steps with an optional concurrency suffix, up to 100,000 indices. Watches of external jobs lack a captured array inventory. Very large, heterogeneous or unusually configured jobs may need manual reconciliation.

Completion/failure or a spent polling budget enqueues one durable parent wake for synthesis. Changed observations are recorded locally; polling errors receive throttled harness notices. Budget exhaustion is `watch-stopped`, never assumed completion. `stop-watch` stops future checks; it does **not** call `scancel`. General `stop` cancels model work/subagents, while already submitted remote jobs and their watches remain independently tracked. Resume a stopped watch with adoption. A new watch of the same existing record returns that record. See the [Slurm accounting manual](https://slurm.schedmd.com/sacct.html) for site-dependent accounting fields and retention behavior.

## Bounded subagents

The daemon owns subagents separately from the lead’s provider process, so a completed parent response does not kill a Clawstrum research subagent. Each subagent gets a fresh native session, narrow brief, explicit source paths, and its own artifact directory; it retains full host access to the supplied project. The lead receives a bounded result and must inspect/synthesize the evidence.

| Role         | Default Claude alias | Default effort | Budget |
| ------------ | -------------------- | -------------- | ------ |
| `explorer`   | `haiku`              | low            | none   |
| `log-reader` | `haiku`              | low            | none   |
| `lit-reader` | `sonnet`             | medium         | none   |
| `analyst`    | `sonnet`             | high           | none   |
| `coder`      | `sonnet`             | high           | none   |
| `thinker`    | `sonnet`             | high           | none   |
| `checker`    | `opus`               | high           | none   |
| `reviewer`   | `opus`               | high           | none   |

The first five roles answer either “what is there” or “make this change”. `thinker` develops a direction the lead has already chosen: design detail, tradeoffs, derivations and an implementation sketch concrete enough to cost it, with every claim marked as derived from inspected evidence or assumed. It does not argue against the direction. Judging is split in two: `checker` asks whether one artifact is true against its sources and proposes nothing; `reviewer` judges a slate, result, draft or figure in one of two stages set by the brief, `direction` (work in progress: is it promising, what does it need; nothing is cut) or `final` (a referee with a slot budget): it first writes the story the items tell, the best story they could tell, the missing link and the lead, then gives every item one verdict (`main`, `fix`, `develop`, `supporting`, `dead_end`, `cut` in the final stage only, `stop` for plan items only). Its cuts are proposals that wait for the user. Both cite `path:line` and a verbatim quote, and the harness checks the quotes before the lead reads them; see [Thinker, checker and reviewer](orchestration.md#thinker-checker-and-reviewer).

Default roles select the Codex models `gpt-5.6-luna`, `gpt-5.6-sol` or `gpt-5.6-terra` (see `src/research/config.ts`); a custom role without `models.codex` inherits the selected account model. No assumption is made that a particular Codex model is cheaper or that token counts reveal subscription cost. Role prompts, descriptions, model overrides, effort and `maxTurns` are configurable. Role `maxTurns` and `workers.timeoutMs` default to `0` (no limit). The lead's periodic progress check (`workers.checkMinutes`) is what stops a stuck subagent instead. Optional role `maxTokens` and Claude-only `maxBudgetUsd` add observed-token and native estimated-cost limits; see [resource accounting and continuation](research-continuity.md). `workers.roles`, when specified, replaces the default role map. Claude uses its SDK turn cap. Codex subagents use the bundled App Server for live steering and usage updates. It lacks that turn cap, so Codex stops on the first completed non-message/non-reasoning item beyond the configured budget; this can overshoot by one completed tool item. Neither cap measures dollars or limits the duration of an individual external job. `max` role effort maps to `xhigh` for Codex.

A role also names the installed skills its subagents receive, resolved against the same two directories the lead reads. The lead is given the whole inventory because it decides what the turn is; a subagent has one brief, and a catalog of workflows it will not use is prompt it pays for on a model chosen to be cheap. The named skills arrive as a catalog in the subagent's instructions, plus hints in the prompt for the ones whose declared triggers match words in the brief. By default `analyst` carries `theory`, `coder` carries `iterate` and `thinker` carries `brainstorm`; the three search roles carry none, and these assignments are a starting point rather than a measured result. A role naming a skill this installation does not have is recorded in the subagent's `research_worker_route` event as `skillsMissing` and does not fail the dispatch, because a role travels with the configuration while skills travel with the installation.

The subagent's instructions end with its contract, after the role prompt and the skill catalog, since several skills are written for a lead and recommend delegating work a subagent cannot delegate. The contract states where the final message goes, that only its first `resultChars` characters wake the lead while the rest stays in the artifact directory, that bulk output belongs in files under that directory, that the subagent sends no messages and starts no nested subagents, and what its turn budget is. The truncation boundary is named explicitly because it is the one constraint a subagent cannot discover from inside its own run.

Defaults allow two research subagents, with a twenty-minute deadline each and a 4,000-character result summary. Subagent capacity is separate from the main-turn global cap, while both share each account’s concurrency cap. Main turns reserve credentials before attachment preparation. `workers.account` is a preferred profile; the account pool may choose another available configured profile. Role configuration is captured at enqueue; credential routing uses the running daemon’s pool. Overrides with unknown quota buckets conservatively cool the credential after a quota failure.

A failed/empty/cancelled subagent gets an explicit durable status and artifact. Quota/auth errors update shared account state. A running subagent is not automatically replayed on another account after failure, because its edits or job submissions may already have occurred. The lead can inspect partial work and create a new bounded continuation with `research_delegate.resumeFrom` on available capacity. `research_steer` corrects a queued/running subagent without cancellation; transport acknowledgments and uncertain outcomes are durable. Daemon recovery marks interrupted running subagents failed and wakes the lead; queued subagents remain queued. `research_status` can cancel an individual subagent. `stop` cancels that conversation’s queued/running subagents through the control timestamp. Subagent cancellation and daemon shutdown reap supervised processes; remote cluster jobs retain their separate lifecycle.

### Checks on a finished result

Before the lead is woken, a finished result is compared against the subagent’s own `EVENTS.jsonl`, which is written by the harness from observed provider events. It is an observation log, not tamper-proof evidence against a full-host agent. Three conditions are reported: the log has no recorded tool activity; none of the paths the brief supplied appears literally in the event log; and absolute paths cited in the result text that do not exist on disk, up to fifty checked and five named. The log can omit relative paths, equivalent paths or truncated details, so these observations cannot prove a source was never read. Findings ride the wake message beside the summary, because that is what the lead reads. They are caveats and never a block: a subagent that read nothing may still be right, and withholding a result is worse than delivering it with a reason to distrust it.

Nothing here depends on the subagent producing a particular output format. A `research_worker_result` event is recorded on every completed subagent, findings or none, so a check that fires on nothing is distinguishable from a check that is not running.

## Research memory, compaction and provenance

### Notes in the lead's prompt, and finding a note by words

Research notes live in the database table `research_notes`, not in the prompt. So the lead can see that they exist, every lead run gets a short list of the channel's current notes: one line each, `- <date> <title> (id <id>)`, newest first. A note that a later note or a memory review has replaced is left out. The list holds titles only. The lead reads a note with `research_status collection=notes id=<id>`.

The list is built from the database each time the lead's context is read. It is not written into `AGENTS.md`. When a note is saved, replaced or retired, the list changes, and a running lead gets it as a normal `CLAWSTRUM_CONTEXT_UPDATE` like any other changed MEMORY text. Subagents and the background memory passes do not get the list. `research.notesIndex` sets the limits: when more notes exist than `maxItems` or `maxChars` allow, the last line says how many were left out and how to list them (`research_status collection=notes current=true offset=<shown>`).

To find a note by words, call `research_status collection=notes query="width sweep"`. A note matches when every word appears in its title or body (letters match in any case). `%` and `_` in the words match themselves. The search covers only this channel's notes, newest first, and `limit` and `offset` work as usual. `current=true` leaves out replaced notes, with or without `query`. `query` and `current` are refused for other collections.

Research notes now update the Research state subsection of AGENTS.md MEMORY. Original note bodies and explicit replacement links remain in SQLite/raw history; superseded managed blocks leave active memory. A note condensed or removed from current memory is not reconstructed on later unrelated writes. The `memory_update` tool handles revisions to free-form prose, and `checkpoint` writes Current work. Active job/subagent state is rendered into the same document from SQLite. Separate RECORDS.md, STATE.json, MEMORY.md and CHECKPOINT.md are retired by migration.

Native compaction has one preservation/restoration hook and no second model. Long-term consolidation uses a dedicated subscription call over complete resumable history chunks, committing memory before planned native rotation. Both mechanisms work independently of the research profile. See [memory lifecycle](memory-lifecycle.md) for their different roles and exact guarantees.

Claude input stays open after a result while SDK-observed background tasks remain. Abort/error closes it; startup and absolute deadlines remain active. This lifetime tracking also supports [live steering](live-steering.md) and does not claim to keep native tasks alive across account switching. Portable daemon-owned subagents are the cross-provider lifetime mechanism.

Tool-call recall puts the conversation's own history in front of the lead when it starts a search. On `Grep`, `Glob`, `WebSearch` and `research_delegate`, the Claude PreToolUse hook takes up to six terms from the field that names the search (the pattern, the query, or the head of the brief) and looks for history records containing at least two of them: research notes and claims, provider messages including tool output, compaction summaries and imported transcripts. Up to `recall.maxHits` excerpts come back as context with their record IDs and any superseding record, labelled as past evidence to read with `history action=read` before relying on it. Records from the current run are excluded because they are already in context. The hook never denies and does not run in subagents. It is silent when nothing matches or when the same term set was already answered, and spends at most `recall.maxNotices` notices per run. It uses the FTS index behind ranked history search and creates it on first use; records older than the index are backfilled newest first, one bounded batch per search, and `clawstrum history index` completes the backfill. Each search is recorded as a `research_recall` event with its terms and hit IDs, so its firing rate is answerable from the store. Codex has no equivalent hook. The predecessor deployment reports 130 notices in 47 of 135 sessions over its first three days, with the cited file named in the lead's next 12 tool calls after 81 of them. There was no control, so this bounds the effect from above rather than measuring it.

Message-time recall runs on every lead run with user input, on Claude and Codex alike. Its candidates are this conversation's research notes that the lead no longer has loaded: not superseded, neither its rendered note block nor a `history:note:<id>` citation in the current MEMORY text (the claim table's bare note id does not count), and not already pasted in the current native session. These are ranked by bm25 against the pending user messages (or, under four words, the previous reply alone; otherwise both), and the top `messageRecall.candidates` are put to Jev one at a time (feature `message-recall`) with the message, the previous reply, the note's title, its age in calendar days and the head of its body. Notes scored at least `messageRecall.threshold` are pasted after the skill advice, highest first, up to `messageRecall.maxNotes`, at most 1,500 characters each and 4,000 in total, with a `history read id=note:<id>` pointer when clipped. Pasted text has invisible and bidi controls removed and markup-like tags defused. The screen shares one `messageRecall.budgetMs` budget and the store-wide Jev concurrency limit; a missing key, disabled decisions or an exhausted daily budget inject nothing. Each run records one `research_message_recall` event with every answered candidate and its score.

Validation checks the same conditions in either mode and differs only in whether the tool call proceeds. It notices when Claude uses raw PDF fetching, omits Unpaywall identification, writes unresolved or mismatched citations through Write/Edit, or invokes raw `sbatch`. It also checks absolute write targets against the workspace, Clawstrum home, temporary directory and configured writeRoots in explicit strict mode. There is no implicit memory-file-size denial; current memory is no longer fitted to separate 6,000/12,000-character budgets.

Three further refusals concern how a run spends model capacity rather than what it writes, and `workers.enforceRoles` sets their severity rather than `validation`. Native `Task` or `Agent` dispatch is redirected to `research_delegate`, even if `subagent_type` happens to match a configured role, because an unconfigured dispatch inherits the lead’s model and effort and a subagent billed at lead rates is the expensive half of any fan-out. A native `Workflow` script is refused for the same reason, with the phase count quoted back so the size of what was about to run is visible in the refusal. A subagent is refused any dispatch at all, since a subagent that delegates spends a budget nobody is watching. The predecessor author reports one run with 140 unconfigured subagents issuing 5,317 model calls, every one of them at the top tier, which exhausted a five-hour usage window in a single pass.

`enforceRoles` defaults to `deny` where `validation` defaults to `advisory`, because the two settings answer different questions. Content validation judges what a call produced, and a model given the finding can act on it by revising. Routing judges which process a call should have gone through, where there is nothing to revise and the alternative is available in the same turn, so a finding the model may ignore is how the 140-subagent run happened. `advise` returns the same text as context and allows the dispatch, `off` removes the check, and `validation: off` disables hook checks, while provider-level native delegation controls remain governed independently by `enforceRoles`. None of the three refusals fires where no roles are configured, and none of them touches the lead’s own `Read`, `Write`, `Edit` or `Bash`: working inline is what the refusal leaves the lead, and what it says to do if no role fits.

In strict mode, writes to `.tex`, `.sty` and `.cls` files are refused until the native context has successfully read its writing rules, meaning a `WRITING.md` in the workspace, read directly or through a skill whose name contains “writing”. The successful post-tool event satisfies the check; an attempted or failed read does not. Each native subagent has separate state, reset on compaction. Only prose payloads of at least 300 characters are gated, so an edit to a macro or a typo is not, and the gate stops after three findings per native context between compactions rather than standing between the agent and its manuscript indefinitely. Where the workspace has no rules file the check never fires. The predecessor author reports a single instance, not an independently reproduced rate: a manuscript produced in the predecessor deployment without loading its conventions carried 33 em dashes and 35 bold runs in 3,300 words, and the rewrite after reading them carried none and seven.

`strict`, selected explicitly, turns these into targeted Claude PreToolUse denials with the proper SDK reason; citation writes receive at most one strict correction per run and native agent, with later findings advisory. The write-target and shell-write denials, and the routing denials above whatever `validation` is set to, are not on that budget and repeat on every attempt: none of them is resolved by revising the same content once, so a single correction opportunity would let the next identical attempt straight through. `advisory`, the default, returns every finding as context text and allows the call, which leaves acting on it to the model. `off` disables the checks. Shell-command recognition is deliberately limited and not a shell interpreter. Hooks can run in native Claude subagents and record their agent IDs. None of these mechanisms confines another full-access program or protects an editable ledger from its OS owner.

Independently of `validation`, the same Claude PreToolUse hook prefixes every `Bash` command, for leads and subagents alike, with `renice -n <research.toolNice> -p $$` so the command's own shell drops to that CPU priority while the daemon and every `claude` process stay at the default priority; the next `Bash` call starts a fresh shell back at priority 0, and `research.toolNice: 0` turns the prefix off. A command that already begins with `renice` or `nice` is left alone. Codex has no PreToolUse hook, so this has no effect on Codex leads or workers.

Both providers also receive citation review before new outgoing messages, final results, file captions and prose attachments enter the outbox. Advisory mode records findings and allows delivery; strict mode holds the first problematic proposal and requests correction. The outgoing correction budget is shared across all routes for one logical input and survives retries and provider changes.

That same review measures the message against ceilings of 25 lines and 2,000 characters, either of which can be set to zero to drop that half of the check. Only the message body is counted; an attached document has no reason to be short. Length shares the one correction opportunity with citations rather than claiming a second, because a reply long enough to trip the ceiling and wrong enough to trip a citation is one reply to fix and not two turns to spend. The feedback asks for a cut rather than a rewording and names what to drop first, which is the material about what was checked and turned out fine. Register, structure and tone are deliberately not checked, since those are judgments about a message rather than measurements of one. The predecessor author reports that 63 percent of 905 sent messages exceeded a prompted ceiling. This motivates a measurable check; it does not establish that the Clawstrum intervention improves brevity or usefulness. That requires matched outcomes after feedback. Remaining findings after that opportunity are recorded and delivery proceeds. Existing final ownership, quiet scheduled responses and payload idempotency remain intact. Codex native file edits have no equivalent Claude hook, but the explicit scan tool and outgoing review work on both providers. See the [six-request review and implementation details](hooks-and-gates.md).

Outbox records now distinguish agent, harness notice, subagent and provider origins. Discord labels non-agent origins explicitly. The implementation uses known origin rather than classifying prose by keywords. Current subagent results enter the lead’s queue rather than being posted directly; provider reasoning remains inside its SDK.

## Tests

The tests exercise HTTP/extractor fixtures, metadata mismatches, cache corruption, notes/context continuity, schema migration, Slurm submission ambiguity/recovery/arrays, subagent ownership/capacity/cancellation/recovery, Claude hook shapes/background lifetime and real MCP processes. Authenticated Claude and Codex subagents are exercised by the orchestration rollout checks. Live Slurm submission, public full-text endpoint availability and long-duration native background operation still need site acceptance; fixture tests do not establish those outcomes.
