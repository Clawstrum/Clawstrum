---
name: onboarding
description: First conversation after setup. Learn who the user is and what they work on, set up one channel per project, and bring in their own skills, tools and data, so the agent is theirs from the start.
triggers: onboarding, get to know me, set me up, first steps, set up my projects, import my skills
not_for: Changing Clawstrum later on (customize); a single new skill or tool server on an installation already set up (customize).
examples: hi! | let's get started | set up a channel for my second project | import my skills from this folder
---

Run this as a conversation, a few questions per message, not a form. Keep each message short. Everything you write goes in plain files the user can read and edit later, and nothing is copied, installed or written without their yes. Before any write to `AGENTS.md` or `config.json`, show the user the edits you plan and ask once; write only after they agree. `$CLAWSTRUM_HOME` is `~/.clawstrum` unless set; the home `AGENTS.md` there is read by every channel.

1. Say who you are in one line (your name is in the first line of the home `AGENTS.md`) and that a few questions will make you useful faster; the user can skip any of them. On a new installation Clawstrum asks you at the first start to write this first message before the user has written: then also say what the main channel is for, give three or four short ideas for making you theirs, and end with the first question of step 2.
2. The person. Ask: their name, field and role; what they are working on now; how they like answers (short or detailed, casual or formal, how often to hear progress, when to ask before acting). Write the answers as an `## About the user` section in the home `AGENTS.md`, above `## MEMORY`, in the user's own words where possible. Where their answers on length or tone differ from the `## How you talk` section of the home `AGENTS.md`, change that section to match. Long dashes in messages already become plain hyphens; turn that off (`discord.plainDashes: false` in `config.json`) only if they ask. Offer one optional setting and set it only if they want it: a length target that reminds you to keep messages short (`discord.sendAdviceChars`, for example 1200). If they write papers, offer a writing-rules file: copy the example that ships next to this skill (`$CLAWSTRUM_HOME/skills/onboarding/WRITING.example.md`) to `$CLAWSTRUM_HOME/WRITING.md`, go through it with them and delete every rule they do not hold. Tell them that once the file exists, a long write to a `.tex` file is refused until the rules have been read in that run.
3. Projects. Ask which projects they want to work on with you. Suggest one Discord channel per project, so each keeps its own memory and files. After they agree, for each project:
   - run `clawstrum setup --add-channel <NAME> --json`: it finds or creates the text channel and adds it to `discord.channelIds`, and the running agent picks it up within seconds, with no restart. If it says the bot may not create channels, ask the user to make a text channel with that name, then run the same command;
   - add a `## Projects` section to the home `AGENTS.md` with one line per project: channel ID (from the command's JSON), project name, one sentence on its goal, its main folders;
   - ask the user to write in each new channel what the project is, so its memory starts with that;
   - a channel's own memory starts the first time someone writes in it, so nothing else needs creating.
4. Their skills. Ask whether they already have skills or written procedures (for example a folder of `SKILL.md` files, a Claude Code plugin repository, or notes on how they run an analysis). For each one they want: copy it to `$CLAWSTRUM_HOME/skills/<name>/SKILL.md`, check it has the frontmatter fields this file has (`name`, `description`, `triggers`), and tell them in one line what you added. Procedures that exist only as notes become a short skill only if they say yes.
5. Their tools. Ask about tool servers (MCP) they use, such as a lab database, an instrument or a search service. For each: an entry under `mcpServers` in `config.json` (`command`, `args`, `env`; secrets stay in `env` or the private `.env`, never in `AGENTS.md`). Follow the `customize` skill for the details.
6. Their data. Ask where their papers, notes, datasets or databases live. Do not copy them. Add a `## Data` section to the home `AGENTS.md` with each path, what it holds and whether you may write there (read-only unless they say otherwise).
7. Where their work runs. Read the `## Where you run` section of the home `AGENTS.md` if setup wrote one. Ask whether their computing runs on this machine, on other machines or on a cluster. For a cluster ask, a few at a time: which cluster and scheduler (usually Slurm); the accounts they charge and which one for what; the partitions they use for CPU and for GPU work, with time limits and GPU types; where big outputs go (scratch, project storage) and where they must not (a small home quota); how they get Python or other software (the full path of a conda environment, modules to load); and a job script of theirs that worked, whose setup lines you copy into new scripts. Look first where you can and ask them to confirm: `sinfo -s` lists the partitions, `sacctmgr -nP show assoc user=$USER format=account` the accounts. Add a `## Compute` section to the home `AGENTS.md` with the exact names and paths. If you run on a shared login node, add that anything heavier than a quick check goes into a job, never onto the login node. With no cluster, one line on where heavy work runs is enough.
8. Finish. Delete the `## First conversation` section from the home `AGENTS.md`. If `config.json` changed in other ways than `--add-channel` (new channels need no restart), run `clawstrum restart request` without `--wait`. If it answers that coordinated restart needs supervision, the agent runs in a terminal under `clawstrum start`: tell the user to stop it with Ctrl-C and run `clawstrum start` again. Then send a short summary: what you now know about them, the channels and what each is for, the skills, tools and data you added, and where each lives so they can edit it. Say that every later change goes the same way: just ask.

If the user wants to stop halfway, write what you have, keep the `## First conversation` section, and note in it which steps are still open.
